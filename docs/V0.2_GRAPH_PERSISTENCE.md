# Kineo v0.2 — Graph & Persistence

## Goal and compatibility

v0.2 builds on the tagged v0.1.0 editor with an interactive mechanical connectivity
graph, synchronized Graph/Split views, unsaved-document protection, a deliberately
empty New Document action, and standalone report-oriented SVG/PNG exports. The
canonical JSON v3.0 document remains the sole persistent model. No graph layout or
other v0.2-only UI state is written into JSON, and no new JSON fields are required.

The v0.1.0 baseline remains compatible: `jointDefinitions` continues to be a
catalogue of joint templates, while `liaisons` are the actual joint instances.
Existing v3.0 fields and extension properties remain handled by the established
passthrough schema and clone-based conversion path.

## Mechanical graph

`src/model/mechanicalGraph.ts` derives a deterministic undirected multigraph:

- Each `classesEquivalence` entry becomes one graph node, preserving its body ID,
  name, and ground designation.
- Each `liaisons` entry becomes one edge with the liaison ID, type, name, and its
  `classA` / `classB` endpoint IDs.
- `jointDefinitions`, geometry, and `parentId` relationships do not create edges.
- Multiple liaison instances between the same pair of bodies remain distinct
  parallel edges. Unknown endpoints and self-connections are rejected rather than
  repaired or represented as fictitious nodes.
- The model provides adjacency and node/edge/neighbor lookup, connected components,
  isolated and fixed node IDs, parallel-connection groups, cycle edge sets, and
  summary counts. The independent graph cycle rank is `E - V + C`.

The graph is derived from the current document and is not mutated back into it.
`src/model/graphLayout.ts` assigns a deterministic transient position to each node
and separates disconnected components. `MechanicalGraphView` displays nodes and
liaison edges, component boundaries, labels, fixed/isolated cues, and topology
statistics. Users can select nodes or edges, zoom, pan, and fit the graph.

Graph node selection maps to the existing body selection; edge selection maps to
joint selection. The sidebar, inspector, 2D canvas, Graph View, and Split View all
use the same Zustand document and selected-entity state. A graph cycle represents
connectivity only, not a physically closed mechanism or a solved constraint set.

## Split View and persistence lifecycle

Split View places the existing 2D canvas alongside the graph. It does not duplicate
the document or create a separate editing model. View mode, graph positions, camera,
selection, grid visibility, and snapping are interface state and are not serialized.

The store tracks a JSON snapshot of the last saved, newly created, or imported
document. Dirty state compares the current canonical document to that snapshot, so
editing away from and undoing back to the saved state updates the indicator
correctly. Saving JSON marks the current snapshot saved. A valid import or new
document establishes a new clean baseline.

Opening another document or creating a new one prompts before replacing dirty
changes. Declining keeps the active document; accepting replaces it. JSON imports
are parsed and checked against the v3.0 schema and reference-integrity validator
before the active store document is replaced. Errors are surfaced in the header.

## Visual exports

`src/model/planarScene.ts` builds the common 2D scene used by the canvas and exports.
It transforms each geometry point and each joint's two body-local anchors through its
owning body's planar frame, identifies separated anchor endpoints, lays out labels
against geometry and other labels, and calculates fitted scene bounds. The canvas
scales joint glyphs and label typography with zoom. Labels are positioned to avoid
the tested geometry and other label bounds; ordinary body/joint labels do not get
long leader lines, while separated-anchor warnings may use one. Separated pivot
endpoints remain visible, and disagreement receives an explicit distance warning.
Rendering does not adjust the mechanism to make its anchors agree.
`src/model/jointSymbols.ts` supplies shared schematic glyphs to both renderers.

The default slider-crank example is a single static reference pose, not an assembly
solver. It retains a 70-unit crank and 120-unit connecting rod from the earlier
demonstration, places O at the ground origin, A on the crank at 45 degrees, and
derives B on the horizontal slider axis so both rigid-segment lengths and all joint
anchors agree. The slider remains its own translating rigid body; a rectangular body
outline sits between two fixed ground-body guide rails, with ground hatching below
the support. The ground-to-slider liaison remains the existing prismatic joint; no
extra body or joint was added. The 2D editor itself was improved instead of adding a
separate presentation mode, so switching views does not create or mutate document
data.

The symbol layer is deliberately distinct from body geometry: revolute joints use a
ring and center mark, prismatic joints use an oriented rail/slider/support glyph,
fixed joints use a hatched wall, and the other catalogue types have distinct
schematic marks. The prismatic glyph is layered behind any revolute pin that shares
its reference location. A neutral diamond/cross is used for an unknown extension
type rather than depicting it as a pivot or slider. These are engineering-inspired
schematics, not verified ISO/AFNOR reproductions. Body geometry, joint symbols,
ground markers, guide rails, labels, and warnings remain separate render layers.

`src/model/export2d.ts` produces a standalone, white-background SVG from the canonical
2D geometry:

- Local points are transformed using the owning body's planar position and rotation.
- Rectangle geometry is rendered from its local corners; other supported point
  geometry is emitted as a polyline.
- Body labels, liaison symbols and labels, pivot attachment markers, and an oriented
  ground marker are included. Joint and ground symbols respect planar orientation.
  Circular attachment markers are deliberately omitted for a prismatic joint so it
  is not mistaken for a revolute joint. The slider guide and hatching belong to the
  fixed ground geometry; the slider remains a separate rectangle.
- SVG labels use high-contrast neutral colors suitable for printing. PNG toolbar
  actions target 1600 px or 2400 px width and preserve the SVG aspect ratio.
- Text and IDs are XML-escaped. Missing geometry body references fail explicitly.
- Bounds include rendered geometry and annotations, with a non-zero minimum image
  size and padding.

PNG export renders that SVG through a browser image and canvas at the selected target
width. Invalid SVG dimensions, unavailable browser canvas support, failed image
decode/encode, and dimensions beyond the configured `8192` pixel edge /
`32,000,000` pixel area limits are explicit errors. Temporary object URLs and
download links are cleaned up.

**Nouveau** creates a valid empty JSON v3.0 document. **Exemple** explicitly loads the
slider-crank demonstration. Startup continues to show the demonstration for the
existing landing experience.

JSON v3.0 remains the editable and reopenable document format; SVG/PNG exports are
visual artifacts only.

## Verification

The implementation was verified with 49 Vitest tests across 5 test files,
TypeScript, ESLint, a production build, and both development and production npm
audits. The suite covers empty and connected graphs, disconnected components,
isolated bodies, parallel edges, open and closed chains, multiple independent
cycles, the slider-crank and four-bar examples, deterministic layout, document
round trips, store lifecycle, SVG bounds and transforms, PNG dimension guards,
local-anchor transforms and mismatch warnings, rigid-segment endpoint/length checks,
joint glyph differentiation and layering, and collision checks for both standard
and dense label fixtures.

Browser checks against the Vite development server verified Graph and Split
rendering, cross-view selection and inspector synchronization, graph-node removal
and undo, dirty new/open behavior, actual toolbar-generated SVG/PNG/JSON Blobs,
empty and slider-crank documents, a four-bar visual fixture, dense labels, and a
deliberately inconsistent-anchor warning. The corrected slider-crank was inspected
in the canvas, then actual toolbar SVG and PNG Blobs were captured and visually
inspected. The SVG had 14 geometry records and 4 liaison records; its white canvas
was 361.56 x 228.80 SVG user units. The valid PNG Blobs were 1600 x 1013 and
2400 x 1519 pixels. The captured JSON content was re-imported through the
application's file input and structurally compared after another save.
See [`TEST_RESULTS.md`](./TEST_RESULTS.md) and
[`FINAL_VALIDATION_V0.2.md`](./FINAL_VALIDATION_V0.2.md) for evidence and
limitations.

## Remaining limitations and next work

- The graph provides topology analysis only. It does not compute mobility,
  hyperstaticity, geometric closure, or mechanism motion.
- 3D editing, solving, animation, and formal certification of standardized symbols
  are out of scope.
- Graph positions and camera state are transient, not saved in the JSON document.
- Dense diagrams with many long labels and anchor warnings remain visually busy even
  though the representative collision fixture has non-overlapping label bounds.
- The default reference pose presents a mechanically closed static geometry only;
  it does not prescribe or simulate a motion cycle.
- Browser verification used the development server and captured the Blobs emitted by
  the real toolbar actions. It did not independently verify OS-managed download
  destinations or a deployed GitHub Pages build.
- Formal ISO/AFNOR conformance and collision-free presentation for every possible
  imported mechanism have not been independently established.
- `package.json` is `0.2.0`; no v0.2 commit, tag, push, or publication was created.
